::: section | Effort
Keep the notebook running while you work. A notebook is the web page where you write Python. A cell is one block in a notebook that you run on its own. Cells run in the order you click them, not the order they sit in on the page. A name defined in a cell you never ran doesn't exist yet.

When you come back to a lab, restart the notebook and run every cell from the top. It takes a moment, and it clears a whole class of confusing errors.
:::

::: section | Failure
Something breaks every week. That's expected. Start early, because a week is budgeted at just under six hours and has little slack.

Read the error before you search it. Python prints a block of text called a traceback when a line fails. Its last line names the error and says what went wrong. Read that line first. Find the line of your own code in the traceback, then print the value just above the line that failed. Change one thing and run it again.

Searching the whole message first returns somebody else's problem, because most of that text is Python's, not yours.
:::

::: section | Time management
Start the lab early in the week. A model call isn't instant. Each one takes a few seconds, and a lab makes many of them.

Then add your reruns. You'll change one line and run the cell again, over and over. Budget the model's time as well as your own, and a lab stops feeling rushed.
:::

::: section | Study skills
Week 0 is the Python on-ramp, and it stays open all term. Use it the moment a week's code stops making sense.

You don't have to work through it in order. Each section stands on its own. If week 3 hands you a KeyError, open the week 0 section on dictionaries. A dictionary holds values by name, and that error means the name you asked for isn't in it.
:::
