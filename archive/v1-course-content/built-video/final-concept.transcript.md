# The last six days

A text version of the concept video. Every word spoken, in order.

## The last six days
Day fifty to day fifty five. Nothing new is taught in this block. You hand in three things, and all three come from work you already did. Here is what each one asks for, and in what order.

## Four dates, and one of them is a close

1. Day 51, late work from weeks 1 to 7 closes
2. Day 52, Part B, the findings report
3. Day 54, Part A, the exam
4. Day 54, Part C, your walkthrough

Start with the date that takes points away rather than giving them. Day fifty one is the hard close on late work from weeks one through seven. After that day those points are gone. Clear that backlog first. Day fifty two is Part B, the findings report. Day fifty four is Part A, the exam. The same day, Part C, a three minute walkthrough of your own repository. The report lands first on purpose. Writing it is exam review.

## Run the harness one more time.

> Your newest file in runs/reports is the source
> for every number in the report.

Before you write anything, run the harness once more. Seed the target, start the app, then run the whole suite. Your newest file in the reports folder is the source for every number you quote. Do not quote a run from last week. Your code has changed since then.

## Eight headings, the first four

1. What was tested, and how
2. Authorization basis
3. Evidence
4. Framework identifiers

Both findings are written on the same eight headings. Do not rename one, and do not skip one. An empty heading tells you what is missing before your reader finds it. What was tested, and how. The case, the prompt, and how many trials. Authorization basis. The clause that allowed the test, and the address you tested. Evidence. A side effect, an audit row, or a canary, pasted in. Framework identifiers. The OWASP entries and the ATLAS techniques, copied from your case file.

## Eight headings, the last four

1. Severity
2. Remediation applied
3. Verification
4. What still remains

Severity. One rating from the table, and the reason you chose it. Remediation applied. The change you made, and the file and function you made it in. Verification. The re-run result with its rate, next to the benign baseline. What still remains. The defect you know is left. This heading is never blank. Finding one is the fix you built and verified in Part A. Finding two you specify in writing, and you do not build it.

## A fix you write instead of building

1. The file and the function
2. The rule you would put there
3. The case, and how many trials
4. What the detector would look at
5. Which result would count as fixed

Pick a second weakness your harness found, then write the fix instead of building it. Name the file and the function you would change. Say what rule you would put there. Name the case you would run, and how many trials. Say what the detector would have to look at. Then say which result counts as fixed, and which one does not. The bar is one sentence. A classmate could build it without asking you a question.

## Two results, side by side

1. **The attack case, re-run.** With its rate. Blocked five of five and one of five are different findings.
2. **The benign baseline.** Normal use still works. A fix that breaks the product is not a fix.

The Verification heading needs two results, side by side. First, the attack case re-run, with its rate. Second, the benign baseline, showing that ordinary use still works. One result without the other proves nothing.

## Three ways good work loses points

1. Evidence that is only the model's account
2. A status word with no rate
3. A verification with only half the picture

Three things sink reports that are otherwise good. First, evidence that is only the model's account of what it did. Quote the outbox file, the audit row, or your canary token instead. Grade the world, not the prose. Second, a status word with no rate next to it. Vulnerable hides the gap between one of five and five of five. Always give the rate. Third, a verification with only half the picture. The attack blocked, and the benign baseline never mentioned.

## Nine hundred words, and it is hard.

> There is no minimum. Cutting is part of the assignment.
> The 150 word question at the end is counted separately.

The report has a nine hundred word cap and it is hard. Nothing after word nine hundred is read or graded. There is no minimum. A short exact report beats a long vague one. The last question is separate, and it gets one hundred fifty words. It asks what defect you know remains in your fix. Every control has an edge it does not cover. An answer of none scores zero.

## Name the weakness class

1. Prompt injection
2. Excessive agency
3. Insecure tool authorization

The exam is three hours, one attempt, and open book. Some items show an agent setup you have never run, so practice on a case file you did not write. Then name the weakness class. There are three of them. Prompt injection is text the model treats as an instruction when it was meant to be data. Excessive agency is the agent taking an action nobody approved. Insecure tool authorization is the tool never asking who is calling. For each one, say what evidence proves it, and what fix holds five of five.

## You still finish.

> Pull the harness-working branch on day 50. Run it against
> your target. Say so in your report. That caps the artifact
> at 80 percent, and never a zero.

If you are behind right now, you still finish this course. On day fifty, pull the harness working branch your instructor published. Run it against your target and collect real results from it. Then say so in your report. That caps the artifact at eighty percent, never a zero. People use that branch every term. That is normal, not a sign of falling behind. One last time, the sentence this course opened with. Scope first, technique second.
