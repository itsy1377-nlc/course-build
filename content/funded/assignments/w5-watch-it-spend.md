::: intro
Predict what a runaway loop costs, build one on a burnable key, and watch the
bar drain. Then fill in the cap and the approval gate. Fifteen points, due day
35. Ten of those points need a real gateway run.
:::

::: scope | Authorization and Scope
Work with three things only:

1. The practice target this course supplies.
2. The agent you built.
3. A model reached through the school gateway, using your own token.

The runaway runs on the burnable key your instructor issues you. It has a small
ceiling and it is meant to be spent. Never use another student's key, and never
point either key at anything outside this list. Clause 1 and clause 3 of the
Rules of Engagement page in Start Here hold the full rules.
:::

::: directions | Directions
1. Open the week 5 notebook and run the setup cell. Wait for it to print ready.
2. Before you run anything, write your prediction in cents. Show the arithmetic:
   the price, the step limit, and the size of the conversation.
3. Load your burnable key. Check that the notebook prints its ceiling.
4. Run the runaway cell and watch the budget bar. Let the run end on its own.
5. Open `show_raw()` and add up the cost stamps. Write that total down.
6. Open the gateway ledger for your key. Put its total beside yours. Say whether
   they agree, and by how much if they do not.
7. Fill in the one blank condition in `budget_guard`. Run the runaway again.
   Name the line in the record where the cap ended it.
8. Report the cost before the cap and the cost after it. Give the difference.
9. Fill in the one blank condition in `approval_guard`, using the tools your week
   1 record marked irreversible.
10. Run your week 4 ticket text once with the gate on. Then run an ordinary
    request that needs the same tool for a good reason. Cite the approval event
    line for each.
11. Run twenty ordinary requests with the gate on and count the approval cards.
    Multiply out to a shift size you name, and write one sentence on what that
    number does not settle.
:::

::: callout tip | The two mistakes that cost people points
The first is writing the prediction after the run. A prediction that matches
perfectly is the one a grader looks at hardest, so write yours first and leave
it alone.

The second is reporting one cost total instead of two. The ledger row and your
own arithmetic are separate records, and putting them side by side is the work.
:::

::: callout note | If the gateway is unavailable
Ten of these points are graded from a session the gateway recorded: the ledger
row, the cap, and the gate. If your instructor declares the gateway down, those
ten wait and the deadline moves. They are not replaced by an offline run.

The other five are earnable either way. Your prediction and its arithmetic come
before any call, and the approval count works against the offline model. The
notebook stamps any report it produces that way, and the stamp stays on it.
:::

::: grading | Grading Criteria
| What earns it | Points |
|---|---|
| Your prediction in cents, written first, with its arithmetic | 3 |
| Your cost total beside the gateway ledger row, with any gap named | 4 |
| The cap filled in, the run it ended, and the cost before and after | 3 |
| The gate blocking both runs, each cited from the record | 3 |
| The approval count, multiplied to a shift, with one limit named | 2 |
| **Total** | **15** |

The middle three rows are the ten points that need a real gateway run. Any size
and any outcome counts. A prediction that was badly wrong loses nothing.
:::
