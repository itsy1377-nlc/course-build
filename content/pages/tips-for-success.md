::: intro
Every item here comes from a way students have gotten stuck before.
:::

::: callout time | Plan the hours before the term starts
Open a calendar now and block the wider figure. Four sittings a week beat one
long day.

Each Overview page itemizes its own week, so plan from those numbers.

If those hours are not available this term, talk to an advisor now.
:::

::: steps | A weekly routine that works
1. **Read the Overview page early.** It says what is due and how long it takes.
2. **Read the Content page before you touch the lab.** Otherwise you spend your
   time confused instead of building.
3. **Do the outside reading midweek.** It is capped at 45 minutes.
4. **Start the lab with days left, not hours.** Setup problems take a day to
   solve.
5. **Submit on Saturday.**

Every week has at least four pages, so the same routine works each time.
:::

::: section | Ask on day one
The most common way to fail here is to get stuck quietly.

A student stuck on Tuesday who posts on Tuesday loses an hour. One who waits
until Sunday loses the week.

So set a rule: **thirty minutes of no progress, and you post.** Include the exact
command and the exact error text. Never paste your API key.
:::

::: callout warning | Week 3 is the hard one
Up to week 3, your script calls the model. From then on, the model calls your
function. That flip confuses almost everyone.

The Week 3 checkpoint is pass or fail. A working branch is published on day 18.

If week 3 feels hard, nothing has gone wrong.
:::

::: section | Run the tests from the start
```
python -m pytest tests/ -q
```

Run it the moment you begin, so you see what failing looks like. Run it after
every change, not on Sunday night.
:::

::: callout tip | Four small things that pay off
1. **Work offline first.** The labs ship with an offline provider.
2. **Keep your evidence.** Quiz items ask for values from your run files.
3. **Write your finding the day you run the attack.**
4. **Back up your repository** somewhere other than one laptop.
:::
